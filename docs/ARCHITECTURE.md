# 🏗️ Архитектура WinState

> Статус: **архитектурное ядро `0.1.0-alpha.1`**.

WinState строится вокруг безопасного конвейера:

```text
Profile → Validation → Discovery → Diff → Plan → Confirmation
              │                                  │
              └──────── Diagnostics              ▼
                                           Checkpoint
                                                ▼
                                              Apply
                                                ▼
                                             Verify
                                                ▼
                                           Transaction
                                                ▼
                                             Rollback
```

## Границы модулей

| Модуль | Ответственность | Запрещённые зависимости |
|---|---|---|
| `WinState.Domain` | ресурсы, состояния, действия, транзакции, контракты | Windows API, YAML, SQLite, CLI |
| `WinState.Core` | валидация, граф зависимостей, планирование | UI, конкретные провайдеры |
| `WinState.Cli` | команды, вывод, exit codes | системная бизнес-логика |
| будущий `WinState.Windows` | безопасные Windows-адаптеры | UI |
| будущий `WinState.Storage` | SQLite, baseline, ownership | CLI |
| будущий `WinState.Providers` | конкретные типы ресурсов | прямое управление транзакциями |

## Главные правила

1. **Сначала план.** Изменение системы без execution plan запрещено.
2. **Идемпотентность.** Повторное применение не создаёт лишних действий.
3. **Проверка результата.** Exit code внешней команды не считается доказательством успеха.
4. **Минимальные права.** Повышение прав запрашивается только для конкретных действий.
5. **Rollback — свойство действия.** Нельзя обещать откат там, где он технически неполный.
6. **Нет секретов в логах.** Секретные значения заменяются ссылками.

## Поток данных

Провайдер преобразует системные данные в `StateResource`. Core сравнивает желаемое и текущее состояния и формирует `PlannedAction`. Apply Engine в будущем будет исполнять только проверенный DAG действий, сохранять checkpoint и вызывать `VerifyAsync`.

## Текущий вертикальный срез

На этом этапе реализованы:

- доменные типы;
- интерфейсы провайдеров и rollback;
- модель профиля;
- базовая проверка профиля;
- bootstrap-чтение YAML-заголовка и environment-секции;
- детерминированная топологическая сортировка действий;
- модель транзакций;
- CLI-команды `--help`, `--version`, `architecture`, `validate`;
- unit-тесты и CI.

Системные изменения Windows **ещё не выполняются**. Это осознанная граница первого архитектурного этапа.
